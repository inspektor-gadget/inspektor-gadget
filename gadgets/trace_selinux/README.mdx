# trace_selinux

The `trace_selinux` gadget traces SELinux AVC (Access Vector Cache) audit
events. By default it reports access denials, telling you which process, in
which container, was denied which permission, along with the source and target
SELinux security contexts and the target object class.

The denied/requested/audited permissions are decoded from the kernel
access-vector bitmasks into permission names (e.g. `{ execute_no_trans }`) in
the `denied_perms`/`requested_perms`/`audited_perms` fields, mirroring how
denials appear in the host audit log. Kernel and user-space stack traces leading
to the audit event can also be collected (see the `kstack` and `ustack` fields).

This is useful for debugging SELinux policy issues in containerized workloads:
instead of digging through the host audit log and manually correlating PIDs to
containers, the gadget reports the offending container directly.

## Requirements

- The node must have SELinux enabled (`CONFIG_SECURITY_SELINUX=y`) and the
  `avc:selinux_audited` tracepoint available (Linux 4.16+).

## Flags

### `--denials-only`

Only report AVC denials. Set to `false` to also report audited events that were
allowed (e.g. matched by an `auditallow` rule).

Default value: `true`

### `--collect-kstack`

Collect the kernel stack trace that led to the AVC audit event (exposed in the
`kstack` field).

Default value: `true`

### `--collect-ustack`

Collect the user-space stack trace of the process that triggered the AVC audit
event (exposed in the `ustack` field, with symbolized frames in
`ustack.symbols`).

Default value: `false`

## Visualizing stack traces

In the default table view, a stack trace is rendered as a single truncated line.
To see the full call path, either select a structured output format or focus the
columns:

```bash
# Full kernel + user stacks, one frame per line
$ sudo ig run ghcr.io/inspektor-gadget/gadget/trace_selinux:%IG_TAG% \
    --collect-kstack --collect-ustack -o yaml

# Table focused on the stack columns
$ sudo ig run ghcr.io/inspektor-gadget/gadget/trace_selinux:%IG_TAG% \
    --collect-kstack --collect-ustack \
    --fields k8s.containerName,proc.comm,tclass,denied_perms,kstack,ustack.symbols
```

See the [Stack traces](../../docs/reference/stack-traces.mdx) reference for more
on symbolization (`--symbolizers`, `--collect-build-id`, etc.).

### Flamegraph view

When stack traces are collected, the `selinux` data source can also be rendered
as a flamegraph (in environments that support the flamegraph view, such as the
web UI). Each AVC audit event is treated as one sample, so the flamegraph
highlights which call paths trigger the most denials. The samples are grouped
hierarchically by container (`runtime.containerName`), process (`proc.comm`),
target object class (`tclass`) and denied permissions (`denied_perms`), then by
the user-space stack (`ustack.symbols`) and finally the kernel stack (`kstack`).

Make sure to collect the relevant stacks so the deeper levels are populated:

```bash
$ sudo ig run ghcr.io/inspektor-gadget/gadget/trace_selinux:%IG_TAG% \
    --collect-kstack --collect-ustack
```

## Guide

<Tabs groupId="env">
    <TabItem value="kubectl-gadget" label="kubectl gadget">
        Start the gadget in a terminal:

        ```bash
        $ kubectl gadget run trace_selinux:%IG_TAG% -A
        K8S.NODE         K8S.NAMESPACE    K8S.PODNAME      K8S.CONTAINERNAME  COMM             PID        SCONTEXT                       TCONTEXT                       TCLASS         DENIED_PERMS
        ```

        On another terminal, trigger a SELinux denial from inside a container,
        for example by trying to access a path the container's domain is not
        allowed to access:

        ```bash
        $ kubectl exec -ti mypod -- cat /etc/shadow
        ```

        Go back to the first terminal and observe the denial, attributed to the
        container:

        ```bash
        K8S.NODE         K8S.NAMESPACE    K8S.PODNAME      K8S.CONTAINERNAME  COMM             PID        SCONTEXT                       TCONTEXT                       TCLASS         DENIED_PERMS
        minikube         default          mypod            mycontainer        cat              728870     …r:container_t:s0:c1,c2         …:unlabeled_t:s0                file           { execute_no_trans }
        ```
    </TabItem>

    <TabItem value="ig" label="ig">
        Start the gadget in a terminal:

        ```bash
        $ sudo ig run trace_selinux:%IG_TAG% --containername mycontainer
        RUNTIME.CONTAINERNAME  COMM             PID        SCONTEXT                       TCONTEXT                       TCLASS         DENIED_PERMS
        ```

        On another terminal, run a container that triggers a SELinux denial:

        ```bash
        $ docker run --name mycontainer -ti busybox cat /etc/shadow
        ```

        Go back to the first terminal and observe the denial:

        ```bash
        RUNTIME.CONTAINERNAME  COMM             PID        SCONTEXT                       TCONTEXT                       TCLASS         DENIED_PERMS
        mycontainer            cat              733494     …r:container_t:s0:c1,c2         …:unlabeled_t:s0                file           { execute_no_trans }
        ```
    </TabItem>
</Tabs>

The `DENIED_PERMS` column lists the names of the permissions that were denied
for the given target object class, decoded from the kernel access-vector
bitmask (the raw mask is still available in the hidden `denied` field). Use the
`--denials-only=false` flag to also see audited events that were allowed, and
`-o json` to see the full event including the kernel stack trace (`kstack`).
